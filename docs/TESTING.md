Duplicate/late packets, wraparound, short gaps, silence/resume and source-clock resets have explicit handling. Short losses use fading repetition followed by a recovery ramp. ## Preserve delayed audio, 2026-10-09

Build 31 / version 1.2.7 corrects receive-buffer starvation. The old player advanced its RTP position when the buffer was empty, then rejected valid delayed packets as late. It now holds that position when no later packet establishes a real gap, rebuilds the existing bounded reserve after sustained starvation, and accounts for actual missing packets separately. Scheduling pauses of 80–200 ms retain queued speech; pauses above 200 ms and excessive backlog still discard stale audio. Startup reserve limits, playback engine, Watch recording controls and cloud call cleanup stay unchanged.

Both private captures were complete. The iPhone capture had two missing 20 ms packets; the Watch capture had none. Packet arrival pauses, rather than a backed-up codec insertion queue, dominated. Offline replay reduced late discards from 144 to zero on iPhone and 29 to zero on Watch. All received packets decode after the bounded replay drain. Within the original recording interval, every iPhone packet and all non-silent Watch audio were retained; only 12 near-silent Watch tail packets remained buffered at hang-up. Receiver arrival-to-decode p95 fell from about 130 to 83 ms on iPhone and 496 to 377 ms on Watch. These figures exclude the device output queue and are not end-to-end conversation latency.

Accounting for both refill silence and concealment over the actual capture interval, non-packet-generated output fell from 9.60 to 6.62 seconds on iPhone and 4.28 to 3.78 seconds on Watch, including startup wait. Concealment counters alone increase because starvation is now explicitly counted; that is not evidence of more lost packets. These two calls have different content and network timing, and replay is not a recording of the physical speaker. Hardware listening remains necessary. ## Silent simulator call

Boot paired iPhone and Watch simulators, then run:

```sh
bash Tools/direct-simulator.sh WATCH_SIMULATOR_ID PHONE_SIMULATOR_ID
```

The script generates/builds the app, installs it into the simulator and exchanges encrypted audio with a local aiortc peer using generated PCM. It does not play audio or use a microphone. Python 3.13 is used to create its local virtual environment. Set `DOTWATCH_TEST_PYTHON` to an existing compatible environment to avoid reinstalling dependencies.

Set `DOTWATCH_PROBE_DURATION=90` for a longer call, `DOTWATCH_PROBE_MODE=blackhole` to drop UDP traffic, or `DOTWATCH_PROBE_PLATFORM=phone` for iPhone. Set `DOTWATCH_PROBE_ENTRY=widget` to wait for an actual Smart Stack tap. The widget must be added in the simulator first. `simctl openurl` is not a reliable substitute for a real watchOS widget tap.

Other overrides: `DOTWATCH_WORK_DIR`, `DOTWATCH_BUILD_DIR`, `DOTWATCH_SKIP_BUILD=1`. For a personal configuration also set `DOTWATCH_CONFIG` and `DOTWATCH_BUNDLE_ID` to match the generated app.

## Common issues

- **Sending pauses after returning to the Watch Home Screen:** the app already uses file-backed background uploads and handles watchOS URL-session wake tasks. However, sending has two dependent requests: transcription, then message submission. watchOS may defer delivering a background response until the app becomes active, so the second request may wait. Initial session renewal/profile lookup also runs in a foreground session. Keeping the app visible until **Message sent** avoids this suspension point. There is no immediate-delivery guarantee; do not retry solely because it is waiting. See [Apple background-request behavior](https://developer.apple.com/documentation/watchos-apps/making-background-requests).
- **Watch shows the previous build:** in the iPhone Watch app, turn off “Show App on Apple Watch,” wait for removal, then install it again. Recheck its About screen.
- **Smart Stack fails while Call works:** remove and re-add the widget after updating. This resolved a reported CallKit transaction error 6 on the earlier personal build; the precise cache cause is unconfirmed.
- **Sign-in required:** open the iPhone app and reconnect/refresh the login, then open the Watch app for session sync. A Google login within the embedded browser may need its own authentication; it does not reuse arbitrary Google app or Safari cookies.
- **Slow initial connection:** creating and attaching a service call can take tens of seconds. Timing diagnostics distinguish these requests from local media setup.
- **No connection on a restricted network:** this transport has no TURN/TCP fallback. Test an ordinary internet connection with UDP available.
